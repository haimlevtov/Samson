# ADR 0016 — The leaderboard: one view, four columns, and a way out

**Status:** accepted, phase 5
**Date:** 2026-09-07
**Supersedes:** ADR 0012's "no leaderboard" consequence, and ADR 0013's
"Hub holds challenges and a placeholder"

## Context

This is **the first feature in the project that reads another user's rows**, and
invariant #10 forbids that by default: every table has `user_id`, RLS is on, and
application code never touches the service role key. `docs/PLAN.md` deferred the
leaderboard to phase 6 for exactly this reason and said it "needs its own ADR
before any code".

Everything shipped so far has been RLS-scoped by construction. A page loads
`loadHistory(db)` with no `user_id` filter and gets the caller's rows because the
policy says so — the absence of a filter is not a bug, it is the design. A
leaderboard inverts that: it must return rows the caller does not own, which
means something has to step outside RLS on purpose.

The realistic harm is not exotic. `users` holds a display name **and the row is
joined to an auth identity**; `xp_events` holds a training history's worth of
timestamps. A leaderboard that leaks a `user_id` hands out a correlation key; one
that falls back to an email local part when somebody has not set a name turns a
game feature into an address book.

## Decision

**A `security_invoker = false` view exposing four values and nothing else, over
users who have chosen to be there.**

### 1. A view, not the service role and not a policy

Three mechanisms could do this. Only one of them is auditable.

- **A `select` policy allowing cross-user reads on `users`.** Rejected: it
  widens the base table for every query in the app, forever, and the blast
  radius of a mistake is every column in the row.
- **The service role key in a server component.** Rejected by invariant #10, in
  as many words.
- **A view owned by the table owner, running with definer semantics.** Chosen.
  The tables carry no `FORCE ROW LEVEL SECURITY`, so the owner reads across
  users; the view is the only thing that does; and **the view definition is the
  security boundary** — it is a single object, in a migration, that a reviewer
  can read top to bottom.

`security_invoker = false` is stated **explicitly** even though it is the
Postgres default. A reader should not have to know the default to know whether
this view is the boundary, and a future default change must not silently turn
the leaderboard into an empty list.

### 2. Four columns, and the two that are absent matter more

| Column         | Why                                                                                |
| -------------- | ---------------------------------------------------------------------------------- |
| `display_name` | Chosen by the user, for other people to see                                        |
| `lifetime_xp`  | The thing being ranked                                                             |
| `rank`         | A leaderboard without your position is half a feature                              |
| `is_you`       | `user_id = auth.uid()`, so you can find yourself without anyone's id being exposed |

**`user_id` is not exposed.** It is the join key to every other table in the
schema and to `auth.users`. RLS would still refuse the follow-up queries, but
handing out a stable per-user identifier is how a leak becomes a correlation,
and nothing on this surface needs one. `is_you` answers the only question the
client actually had.

**`email` is not exposed**, and neither is anything derived from it — see §3.

### 3. A user with no display name does not appear

`docs/PLAN.md` asks for "an explicit answer to what a user who has not chosen a
display name is called". The answer is that they are not called anything,
because they are not on the leaderboard.

The tempting fallbacks are both wrong. **The email local part** turns a game
into a directory and is the single worst thing this feature could do. **A
generated placeholder** ("Lifter 4821") puts somebody on a public ranking who
never asked to be on one and cannot be recognised on it anyway.

Appearing requires having chosen a name to appear under. That is consent shaped
like a product decision, and it costs nothing: setting a display name is one
field on `/settings`.

### 4. Opting out is a column, and the default is visible

`users.leaderboard_opt_out boolean not null default false`.

**The default is argued rather than assumed.** Default-visible is the weaker
privacy position, and it is chosen because of what is actually exposed: a name
the user typed for other people to read, and a score they generated by using the
game layer. Nothing here is observed, inferred, or sensitive on its own — and
§3 already means nobody appears without having volunteered a name.

The counter-argument is real and is recorded rather than dismissed: consent by
default is not consent, and a user who set a display name for their own profile
did not necessarily mean it for a ranking. If this app ever had real users
rather than a demo cohort, that argument should win and the default should
flip — the column is a boolean either way, so the reversal is one migration and
this paragraph.

### 5. Grants: `authenticated` only

`select` to `authenticated`, never to `anon` — ADR 0003's two independent gates.
An unauthenticated leaderboard is a public directory of names and scores, and
`is_you` would be meaningless with no `auth.uid()`.

## Amended 2026-09-09 — the board shows a level, and the view did not move

The Hub printed `lifetime_xp`. It now prints the **level** that total earns.

**The four columns are unchanged, and no migration was needed.** `levelForXp` is
monotonic non-decreasing, so `rank() over (order by lifetime_xp desc, …)` already
produces a level ordering: it can never put a lower level above a higher one. The
change is a mapping in `src/db/leaderboard.ts`, not a query.

**The level is derived in TypeScript, deliberately.**
`src/gamification/level.ts` is the single definition of the curve, including the
per-step rounding whose AI-NOTE explains why a closed-form sum drifts at the
edges. Reimplementing it in SQL would be a second definition of one number — the
failure this project has recorded three times over, and the reason
`sessions_last_28_days` is read rather than recounted.

**The total order was kept rather than sharing ranks within a level**, which was
the stakeholder's call on 2026-09-09. Level buckets XP, so ranking by level alone
would put a third of the table on one position, and a ladder where that happens
stops being a ladder. XP remains the tiebreak and is never printed.

**§2's privacy argument is strengthened by this, not weakened.** That section
weighs what four columns disclose, and "What this does not guarantee" below notes
that an XP total which only ever rises lets somebody infer roughly when you last
trained. **A level moves a handful of times a year rather than after every
session**, so the same inference is far coarser. `lifetime_xp` still crosses the
view — it is what orders the board — but it now stops at the server component
that renders the level, and no longer reaches another user's browser.

## What this does not guarantee

**The row count is a population count.** Anyone authenticated can page the view
and learn how many users have a display name and have not opted out. For a demo
cohort that is not worth defending against, and it is stated here rather than
left for a reader to discover.

**A display name is user-authored text.** It renders in a React text node, so
it cannot inject markup — but it is also third-party text on a shared surface,
and it is clamped on the way out. The mechanism is shared with the catalogue
sanitiser in `src/llm/safety.ts`; the reason is not. Catalogue text is fenced to
keep it out of a model's instruction channel (invariant #11). A display name is
clamped so a bidirectional override or a stack of combining marks cannot
vandalise the row of somebody who never typed it.

**Rank ties are broken by name.** Two users on identical XP get a stable order
rather than a fair one. It is deterministic, which is what stops the list
shuffling between renders.

**A polled XP total is an activity signal.** `lifetime_xp` has no date bound and
only ever rises, and any authenticated user may read the view as often as they
like. Invariant #4 ties XP to adherence, so a total that moves means _that named
person trained_. Nobody's sessions are exposed, but somebody watching closely
enough can infer roughly when they happen.

This is why the settings copy says "when you last trained can be inferred"
rather than the flat "not your sessions" it said first — the app makes a factual
privacy claim at the moment of consent, and that claim has to be true. Rate
limiting is out of scope (`CLAUDE.md`), so the honest move is to say it.

**Display names are not unique, and impersonation is undefended.** Nothing stops
one user setting their display name to another's, and `is_you` marks only the
reader's own row — so on the app's one shared surface, two identical names are
indistinguishable to everybody except the two people involved. A uniqueness
constraint would be the fix, and it brings its own problem (first come, first
served, on a name somebody else may already use elsewhere). For a demo cohort,
naming it here is the right amount of effort.

## Consequences

- `tests/db/` gains cases for the view **rather than an exemption** — PLAN.md
  phase 6 asks for this in as many words. The RLS coverage test enumerates
  `relkind = 'r'`, so a view is invisible to it: without explicit cases this is
  a hole in the coverage, not a covered surface.
- Two migrations: the column and the view. The column ships first, because a
  view that filters on a column the database does not have is a broken view.
- The Hub's placeholder card, which has been describing this decision in prose
  since ADR 0013, becomes the thing it describes.

## Alternatives rejected

**Rank everybody, filter in the application.** The view would return every user
and the page would drop the opted-out ones. Rejected: the boundary would then be
a `.filter()` in TypeScript, and the row would already have crossed the network.
A security boundary that has to be re-implemented by each caller is not one.

**A `security definer` function instead of a view.** Equivalent in safety and
worse to read: a function hides its shape behind a return type, while a view's
definition is its contract. `accept_challenge` is a function because it
_mutates_; this only reads.
